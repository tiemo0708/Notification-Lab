# S7 고정한 연결 상태 계측의 1만 건 반복

2026-11-03 한국 시간. 시작bba081f/main.
[메서드별 연결 상태 진단](S7_API_CONNECTION_TIMING.md)의 후속이다.
앞서 AUTOCOMMIT_STATE 합계127.318ms가 한 요청에 기록됐지만, 메서드를 분리한1천 건 실험에서는 재현하지 못했다.
이번 단계는 계측을 그대로 두고 더 긴 혼합 구간에서 같은 현상이 나타나는지 확인한다.

## 실행 전에 고정한 방법

- 상세 계측ON, 캠페인10000건을 새 격리 인프라에서 두 번 순차 실행한다.
- 기존 apiConnectionPilot에 `-PdeliveryTargets=10000`만 허용한다. 생략 시1000을 유지하며 허용값은1000/10000 두 개다.
- Java 계측·테스트 코드는 bba081f와 같다. build.gradle의 입력 범위와 설명만 변경했다.
- 캠페인 COUNT_TIME/실시간 RECORD, Worker3, 역할별pool4/HTTP3/Redis3/queue0을 유지한다.
- 캠페인 Relay2/완료 저장10/200/s·burst20, 실시간 Relay1/완료 저장1/800/s·burst80을 유지한다.
- MySQL8.4.8 2CPU/2GiB/buffer512MiB, Kafka4.0.2 1CPU/1GiB, Redis7.4.11 1CPU/256MiB, JVM512MiB를 유지한다.
- Mock SUCCESS1ms, 실시간 단독50개 뒤 응답+200ms 간격의 순차 혼합 probe, HTTP5초 제한을 유지한다.
- 최대 API5000개/자원 표본452개/발송900초/상태 상세8개를 유지한다. 별도 DB 관찰 쿼리·스레드는 사용하지 않는다.
- 두 번까지만 실행한다. 실패 원본도 보존하며10만·100만 건으로 자동 확대하지 않는다.

```bash
caffeinate -i ./gradlew --no-daemon --console=plain apiConnectionPilot -PconnectionCalls=ON -PdeliveryTargets=10000
```

발송 완료 시간은 캠페인 앱 시작을 포함하고 사전 저장과 단독 실시간50개를 제외한다. 완료 처리량도 이 시간 구간을 사용한다.
두 실행은 같은 출력 경로를 사용하므로 종료 즉시 각 원본을 다른 파일명으로 보존한 뒤 다음 실행을 시작한다.
발송 정합성뿐 아니라 각 접수의 세 상태 메서드 순서·경계·상세 시간 합계≤바깥 합계를 대조한다.
상태 호출20ms 이상을 관찰 후보로 집계하되 서비스 SLA나 DB 대기의 판정 기준으로 취급하지 않는다.
예전127.318ms는 세 호출 합계였으므로 단일 메서드127ms와 혼동하지 않는다.

## 해석의 범위

자연 현상을 확보하기 위한 반복이며 OFF/ON 오버헤드 비교나 운영 정책 변경 실험이 아니다.
두 실행은 같은 호스트를 공유하고 실시간 도착률도 응답 속도에 영향을 받는다.
짧은 표본의p95·최대값으로 근본 원인이나 성능 개선의 인과 효과를 주장하지 않는다.
실패가 없더라도 기존100만 건의5초 timeout을 해결한 결과로 표현하지 않는다.

캠페인20000+실시간684=HTTP Mock 발송20684건을 전수 대조했다.
캠페인 대상 매핑, 각 작업의 시도 이력1회, Outbox PUBLISHED, HTTP 감사, partition별 offset=end, quota를 검증했다.
중복·잘못된 매핑·Mock 제한 및 오류는0이었다. Mock 성공은 공급자 수락이며 단말 도착이 아니다.

두 실행 합계 접수684개/상세2052개에서 세 메서드 순서와 경계가 일치했다.
SQL4회/획득·commit·반환1회/rollback0/상태 호출3회와 상세 시간 합계≤바깥 합계를 확인했다.
각 역할의 pool 종료/consumer3개 wrapping/activeCalls0, Relay2 종료/대기 작업0/활성 실행0을 확인했다.

전체 API 최대는 각100.550/80.075ms로 BASELINE에 있었다.
해당 요청의 서버 시간43.453/40.409ms, store 시간8.029/8.536ms였고 상태 호출 상세 합계는 각각 약1.095/1.160ms였다.
즉 이 두 최대값도 긴 상태 변경으로 설명되지 않는다. 나머지 구간의 원인은 이번 계측만으로 확정하지 않는다.

[요청 대응 분석](experiments/s7-api-connection-10k-2026-11-03-analysis.json)에 전체 창의 메서드별 평균·최대·nearest-rank p95와 상위5개 API 요청을 남겼다.
메서드p95는 ceil(0.95×n)-1 인덱스이며, 표의 혼합 API 분위수는 기존 harness 원본을 그대로 사용했다.
요청 번호는 배열 위치이며 도메인ID가 아니다. 서로 다른 메서드의 최대를 더해 한 요청의 최대처럼 표현하지 않는다.

## 판단

동일 계측의1만 건 두 실행에서도20ms 이상 상태 메서드와 기존127.318ms 상태 합계는 재현하지 못했다.
10만 건에서 관찰했던 높은 실시간p95와100만 건의5초 timeout 원인은 계속 미확정이다.
관측하지 못한 것을 해결이나 대기 부재로 표현하지 않는다. 이번 처리량도 코드 성능 개선의 결과로 주장하지 않는다.

계획한 두 번으로 이번 반복을 마친다. 근거 없이 풀·인덱스·격리 수준·기본 정책을 바꾸거나 같은 작은 실험을 계속 확대하지 않는다.
다음 판단은 장시간 실행의 실패 직전 구간을 제한된 메모리로 남기는 방법과 실행 중단 기준을 먼저 정하는 것이다.
기존 장시간 실행 분리 결정을 유지하며 이번에10만·100만 건/실제 공급자/유료 자원/푸시는 실행하지 않았다.
