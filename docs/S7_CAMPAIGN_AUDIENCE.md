# S7: 고정 가상 대상자와 keyset pagination

캠페인에 저장한 `audience=SYNTHETIC_V1`과 `targetCount=N`으로 대상자 집합을 고정한다.
대상자는 순번 1~N이며 수신자 ID는 `synthetic-v1-1`부터 `synthetic-v1-N`까지다.
N은 1~1,000,000이고 캠페인 생성 뒤 정의를 수정하는 API는 없다.

## 왜 고정해야 하나

페이지를 읽는 중 가입·탈퇴·정렬 조건이 바뀌면 같은 페이지 번호가 다른 대상을 가리킬 수 있다.
실패 후 다시 시작할 때 대상이 바뀌면 누락과 중복의 원인을 구분하기 어렵다.
현재 학습 범위는 실제 회원을 조회하는 것이 아니라 **같은 실험을 재현할 가상 집합**이다.
따라서 버전과 상한만 저장하고, 필요한 페이지의 대상만 규칙으로 계산한다.

| 선택지 | 이점 | 비용과 한계 |
| --- | --- | --- |
| 모든 대상을 메모리 목록으로 생성 | 코드가 단순함 | 100만 명 전체를 매번 적재하며 재시작 복구 기준이 별도로 필요 |
| DB 대상자 테이블과 캠페인 스냅샷 | 변경되는 회원 정보와 실제 인덱스를 실험 가능 | fixture 적재·수정 금지·스냅샷 완료·보관 정책까지 필요 |
| 버전이 고정된 가상 집합 + 마지막 키 | 별도 적재 없이 재현 가능, 페이지 크기로 메모리 제한 | 실제 회원 변경·SQL 실행 계획·DB 스캔 비용은 검증하지 못함 |

세 번째 방식을 선택했다. 기존 V8 campaign 정의 한 행이 집합을 결정하므로 새 migration이나
100만 행 seed가 필요 없다. 실제 회원 DB를 연결하는 단계에서는 별도 스냅샷·상한·인덱스 설계가 필요하다.

## 순서와 이어 읽기

정렬 키는 수신자 문자열이 아닌 **숫자 ordinal**이다. 문자열 정렬에서 10이 2보다 먼저 오는 문제를 피한다.
요청의 `after`는 마지막으로 읽은 키이며, 반환 범위는 `after < ordinal <= N`이다.
앞 페이지를 순회하거나 OFFSET으로 건너뛰지 않고 `after + 1`에서 직접 시작한다.
한 번에 최대 1,000개만 만들며 계산·응답 메모리 사용량은 페이지 크기에 비례한다.

예를 들어 N=2,003, limit=1,000이면 다음과 같다.

| 요청 after | 반환 ordinal | nextAfter |
| --- | --- | --- |
| 0 | 1~1,000 | 1000 |
| 1000 | 1,001~2,000 | 2000 |
| 2000 | 2,001~2,003 | null |
| 2003 | 빈 목록 | null |

다음 요청의 limit은 달라도 된다. 동일 캠페인/after/limit은 같은 결과를 재생한다.
마지막 페이지가 limit과 정확히 일치해도 nextAfter는 null이다.
읽은 뒤 다음 키를 저장하기 전에 실패하면 같은 페이지를 다시 읽을 수 있다.

**nextAfter는 읽기 위치이며 발송 완료 checkpoint가 아니다.** 후속 Batch에서는 작업 인계/ACK와
checkpoint 저장 순서를 함께 설계해야 한다. 읽자마자 진행 위치만 확정하면 미처리 대상을 건너뛸 수 있다.
현재 API는 진행 위치를 저장하거나 캠페인 상태를 바꾸지 않는다.

## 조회 API

CAMPAIGN 역할의 비동기 앱에서 다음을 호출한다. REALTIME에서는 404다.
DRAFT와 START_REQUESTED 모두 조회할 수 있고 조회만으로 시작되지 않는다.

```bash
curl 'http://127.0.0.1:8082/campaigns/응답_UUID/audience?after=0&limit=2'
```

응답 형태:

```json
{
  "campaignId": "생성한 캠페인의 UUID",
  "audience": "SYNTHETIC_V1",
  "targetCount": 100000,
  "items": [
    {"ordinal": 1, "recipientId": "synthetic-v1-1"},
    {"ordinal": 2, "recipientId": "synthetic-v1-2"}
  ],
  "nextAfter": 2
}
```

- after 기본값 0, 허용 범위 0~targetCount. 상한과 같으면 정상 종료의 빈 페이지다.
- limit 기본값 100, 허용 범위 1~1,000. 숫자 범위 초과·소수·문자열은 400이다.
- 없는 캠페인은 404, 잘못된 UUID는 400이다. 저장소 장애는 503이다.
- 지원하지 않는 대상 버전이나 손상된 저장 상한을 만나면 503으로 거절한다. 다른 집합으로 대체하지 않는다.
- after는 공개 숫자 키다. 인증 토큰도 아니며 캠페인 ID를 담지 않는다. 클라이언트는 **campaignId와 after를 함께 보관**해야 한다.
  키만 다른 캠페인에 옮기면 그 캠페인의 같은 순번 뒤를 읽는다.
- 각 페이지 요청은 DB에서 캠페인 정의를 읽는다. 대상자 목록은 별도 DB 행으로 저장하지 않는다.

동일 버전에서 같은 순번은 다른 캠페인에도 같은 가상 수신자 ID를 갖는다.
캠페인별 발송 작업 ID는 다음 단계에서 캠페인과 대상 식별자를 함께 사용해야 한다.
시간·앱 인스턴스·시작 상태·난수는 집합을 바꾸지 않는다. SYNTHETIC_V1 규칙은 향후에도 유지하고,
대상 규칙을 바꾸려면 새로운 버전을 도입해야 기존 캠페인을 재현할 수 있다.

## 실제 DB keyset과의 차이

이 구현은 가상 집합의 키를 이용한 순회다. SQL `WHERE id > :lastId ORDER BY id LIMIT :size`를
실행하거나 DB 인덱스 성능을 측정한 결과가 아니다. 실제 회원 집합은 단조 증가 ID 상한만 고정해도
기존 행 삭제나 조건 변경으로 구성원이 바뀔 수 있다. 그때는 불변 fixture 또는 별도 스냅샷과
정렬 키의 유일성, 조회 인덱스, 동일 범위 재시작을 검증해야 한다.

## 검증과 남은 범위

`SyntheticCampaignAudienceTest`에서 10만/100만 대상을 997·1,000 크기로 번갈아 순회한다.
순번 연속성, 총수, 고정 SHA-256을 대조하며 마지막 경계/깊은 키 재개/잘못된 크기/버전 거절을 검증한다.
해시 입력은 각 대상의 UTF-8 `ordinal:recipientId`와 줄바꿈을 순서대로 합친 것이다.
이 값은 SYNTHETIC_V1 매핑의 의도치 않은 변경을 감지하는 기준이다.

| 대상 수 | SHA-256 |
| --- | --- |
| 100,000 | `05c4bfd7158adda6f40c30af79c4d499798d0123af4c2a2cd4529c6c01e8c105` |
| 1,000,000 | `f573d9fac181278ccd18031cd727fc925165fa4e2d4df0d1f3e5d83ea57b9764` |

실제 MySQL/Kafka 앱 테스트에서는 2,003명 집합의 HTTP 페이지, 두 앱 동시 재조회, 시작 전후,
다른 캠페인 생성과 앱 재시작 뒤 이어 읽기, 잘못된 입력과 REALTIME 404를 확인한다.
알림/작업/시도/Outbox 행과 Kafka end offset, Redis 허가 카운터가 0인지 대조한다.

```bash
./gradlew --no-daemon --console=plain test --tests '*CampaignApiTest' --tests '*SyntheticCampaignAudienceTest'
./gradlew --no-daemon --console=plain build
```

실행 결과는 [PROGRESS](PROGRESS.md)에 기록한다. 100만 건 순회는 **가상 대상 열거의 정합성 검사**이며
100만 건 DB 처리·Kafka 발행·공급자 발송 부하 테스트가 아니다. START_REQUESTED는 계속 대기 상태다.
