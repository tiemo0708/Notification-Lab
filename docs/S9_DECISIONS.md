## 1. 외부 API 보호: 발송 속도와 대기 자원을 함께 제어한다

### 문제 상황

Worker를 늘리면 동시에 공급자를 호출할 기회도 늘어난다. 각 프로세스가 자기 메모리에서만 초당 한도를 관리하면
공급자가 허용한 전체 예산을 프로세스 수만큼 사용할 수 있다. 실패한 요청의 재시도까지 별도로 보내면 호출량이 더 늘어난다.
캠페인이 먼저 자원을 점유하면 실시간 알림도 같은 HTTP 연결이나 처리 자리를 기다릴 수 있다.

서로 다른 세 가지 양을 구분해야 한다.

| 제어 대상 | 이 프로젝트의 장치 | 의미 |
| --- | --- | --- |
| 동시에 진행하는 작업과 대기 수 | WorkerAdmission·유한 대기열·HTTP 연결/진입 상한 | 프로세스의 메모리·연결·처리 자리를 보호 |
| 일정 시간에 발급할 호출 허가 | Redis Lua token bucket | 여러 Worker가 같은 공급자 예산을 공유 |
| 공급자 장애 중 계속 호출할지 | 선택적 Circuit Breaker | 실패가 쌓이면 새 호출을 보류하고 복구 탐침을 제한 |

연결 풀의 크기는 동시 연결 수이고 quota는 시간에 따른 허가 수다.
재시도 정책은 이미 실패한 개별 작업을 언제 몇 번 더 시도할지 정한다. 세 장치의 책임이 다르다.

### 대안과 선택 이유

| 대안 | 장점 | 비용과 선택 |
| --- | --- | --- |
| Worker마다 로컬 속도 제한 | 구현이 단순함 | 전체 예산을 공유하지 못하므로 Redis의 원자적 Lua 판정을 선택 |
| DB 선점 후 토큰을 기다림 | 흐름이 짧음 | 발송 전부터 lease와 시도 횟수를 소비하므로 후보 확인 후 DB 밖에서 허가를 받고 다시 선점 |
| 소비 스레드에서 계속 대기 | 구현·비교가 쉬움 | poll과 처리 자리를 점유하므로 정상 LIMITED에는 pause/poll/resume 선택 |
| 토픽만 분리하고 실행 자원 공유 | 적체를 구분하기 쉬움 | HTTP/DB 풀과 Worker 자리에서 다시 경합하므로 역할별 실행·풀·예약 예산 선택 |
| 공급자 장애에도 개별 retry만 적용 | 정책이 적음 | 많은 작업이 각자 실패 예산을 소모하므로 선택적 프로세스별 회로 차단 추가 |

현재 발송 후보의 흐름은 다음과 같다. 완료된 작업의 재전달은 추가 공급자 호출 없이 끝날 수 있다.

```text
Worker 처리 자리 확보
→ 짧은 DB 트랜잭션에서 작업·세대·lease·예산 확인
→ DB 잠금 해제
→ 선택적 Circuit permit과 Redis 허가 확인
→ 새 DB 트랜잭션에서 조건 재검사·발송 시도 선점
→ 트랜잭션 밖에서 HTTP 호출
→ DB에 결과·시도 이력·필요한 재시도/DLQ 인계 저장
→ 해당 Kafka 레코드의 offset 처리
```

허가와 실제 선점 사이에는 다른 Worker가 먼저 상태를 바꿀 수 있다. 재검사를 통해 중복 선점을 막지만
이미 받은 허가가 낭비될 수 있다. 허가를 임의로 환불해 공급자 상한을 넘기는 방식은 사용하지 않는다.

정상 한도 부족은 레코드를 보관한 채 pause하고 poll을 유지한다. 재개 시각은 토큰 예약이 아니므로 다시 허가를 검사한다.
Redis 상태가 없거나 잘못됐을 때는 새 burst를 자동 생성하지 않는다. 기본 오류 정책은 중단이며,
선택적 일시 오류 복구도 알려진 연결 오류만 레코드별 최대 3회 pause 후 중단한다.
이 일시 오류 재시도 예산을 보존하는 맵의 기본 용량은 6개 토픽·파티션이며 명시적 상한은 12다.

역할 분리를 켜면 공급자 전체 rate/burst에서 캠페인 몫을 뺀 나머지를 실시간에 예약한다.
예시 전체 10/10, 캠페인 2/2에서는 실시간 8/8이다. 유휴 몫을 빌리지 않는 대신 캠페인이 실시간 몫을 차지하지 못한다.
이 값은 학습용 정책이며 실제 공급자 한도나 운영 권장값이 아니다.

### 변경 전후 증거

이 항목의 전후는 실패 경계와 자원 점유 방식의 변화다. 같은 부하의 성능 개선율을 측정한 비교는 아니다.

| 확인한 경계 | 기존 문제/대안의 비용 | 보완 후 실제 증거 |
| --- | --- | --- |
| quota 대기 | 소비 스레드에서 기다리면 poll을 계속할 수 없음 | 제어 테스트에서 7초 pause 동안 poll·heartbeat 유지, DB 시도/HTTP/offset/Worker active는 0 |
| 역할 간 발송 몫 | 공유 자원에서는 캠페인이 실시간 자리를 먼저 차지할 수 있음 | 실제 Redis의 독립 클라이언트 4개·동시 요청 48회에서 실시간 허가 8/캠페인 2, 몫 차용 없음 |
| 여러 JVM의 전체 예산 | 프로세스별 로컬 제한만으로는 전체 예산을 묶지 못함 | S9에서 Worker 2개가 모두 pause한 동안 고정 토큰 2개에 전체 HTTP/시도/커밋이 정확히 2개 |
| 공급자 응답 유실 | timeout은 미수락을 뜻하지 않음 | 지연 700ms/응답 timeout 200ms 제어에서 HTTP 시도 3회·Mock 수락 3회·최종 RETRYABLE_FAILURE/DLQ |

S9의 토큰 2개는 새 테스트 예산의 refill 시각을 고정한 제어 조건이다. 운영 리필 절차나 초당 처리량 측정이 아니다.
회로 차단은 프로세스별이므로 HALF_OPEN 탐침 하나도 **JVM별 하나**다. 전역 탐침 하나를 보장하지 않는다.
이미 허가한 호출을 취소하지 않으며, 정상 한도 부족의 전체 대기 시간 자체에 상한을 두지는 않는다.

## 2. 유실·중복 대응: 완료 지점을 나눠 기록한다

### 문제 상황

MySQL 저장, Kafka 발행, 공급자 수락은 각각 다른 완료 지점이다.
DB 저장 뒤 Kafka 전송 전에 프로세스가 종료될 수 있고, Kafka ACK를 받은 뒤 DB 발행 기록 전에 종료될 수도 있다.
공급자가 수락한 뒤 응답이나 DB 저장을 잃으면 외부 실행 여부를 DB만으로 판단하기 어렵다.

| 대안 | 장점 | 비용과 선택 |
| --- | --- | --- |
| 요청 저장 후 Kafka를 직접 전송 | 구성이 짧음 | 두 쓰기 사이 중단 구간이 생겨 같은 DB 트랜잭션에 Outbox 저장 선택 |
| Kafka ACK 전에 발행 완료 기록 | 재조회가 줄어듦 | 미발행을 완료로 오인할 수 있어 ACK 성공 이후 조건부 PUBLISHED 기록 |
| 조회로 중복 여부를 먼저 판단 | 이해하기 쉬움 | 동시 요청의 조회 사이 경합을 막지 못해 DB UNIQUE와 트랜잭션 선택 |
| 외부 결과 미확정 작업을 자동 성공 처리 | 재호출을 줄임 | 실제 미발송을 숨길 수 있어 유한 복구와 UNKNOWN 이력 선택 |
| 오류 레코드를 건너뛰고 진행 | 뒤 작업이 빨리 진행됨 | 미완료 작업의 재처리 기회를 잃으므로 오류/상태별 보관·중단 정책 선택 |

API는 notification·delivery_task·Outbox를 한 MySQL 트랜잭션에 커밋한 뒤 202를 반환한다.
이 응답은 내구성 있는 접수이며 공급자 수락이나 단말 도착은 아니다.
Relay는 짧은 트랜잭션에서 lease를 선점하고, DB 트랜잭션 밖에서 Kafka ACK를 기다린 뒤
소유 토큰이 일치할 때만 PUBLISHED로 바꾼다. Worker는 DB 완료 또는 다음 재시도/DLQ 인계를 저장한 뒤 offset을 처리한다.

### 서로 다른 중복을 서로 다른 키로 처리한다

| 대상 | 장치 | 보장 범위 |
| --- | --- | --- |
| API 재접수 | 선택적 Idempotency-Key·DB UNIQUE·요청 값 비교 | 같은 key/내용은 같은 알림 반환, 다른 내용은409. 키가 없으면 독립 요청 |
| Kafka 이벤트 재전달 | eventId/taskId·영속 상태·세대 확인 | 완료/이전 세대의 이벤트를 추가 공급자 호출 없이 처리 |
| 만료된 작업의 늦은 결과 | lease token·조건부 UPDATE | 새 소유자가 선점한 뒤 이전 소유자가 DB 결과를 덮어쓰는 것 차단 |
| 외부 공급자 중복 실행 | 현재 공급자 멱등 계약 없음 | 수락 후 DB 실패/응답 유실이면 중복 호출 가능성이 남음 |

기본 발송 선점 예산은 최초·재시도·불확실 복구를 합쳐 3회이며 접수 시 고정한다.
지연 재시도는 due 시각과 세대를 영속 저장하고 Relay가 다시 인계한다. 최종 실패는 DLQ Outbox에 남긴다.
DLQ는 자동 성공 처리가 아니며, 선택 재발행은 원본과 새 작업의 계보·이력을 보존한다.

### 변경 전후 증거

| 장애/경계 | 중단 시 증거 | 복구 후 실제 결과 | 해석 |
| --- | --- | --- | --- |
| Relay의 Kafka ACK 후 DB 발행 기록 전 JVM 종료 | Kafka에는 기록, Outbox는 PROCESSING | 같은 이벤트가 Kafka에2개, 공급자 호출/작업 시도는1개 | 이벤트 중복과 완료 작업의 중복 호출 차단을 별도로 확인 |
| Worker의 외부 수락 후 DB 완료 저장 실패 | 실패 파티션 offset 미커밋, STARTED가 남음 | S8의 논리 작업4개에 HTTP 수락5회, DB 완료와 개별 offset 회복 | offset 보존과 외부 중복 방지는 다른 보장 |
| 완료된 요청 이후 API1 종료 | 원래 알림·작업이 DB에 남음 | API2 재접수200·같은ID, 다른 본문409 | S9는 완료 후 재접수 경계이며 응답 유실 직후의 재접수 실험과 구분 |
| timed commit의 WakeupException | 살아 있는 Worker가 중단되는 실제 실패 | 같은 명시적 offset·원래 timeout의 남은 시간으로1회 재시도. 전체 회귀의 S9 실행에서 실제1회 사용 후21개 전수 대조 통과 | 공급자 호출 재시도와 구분. 반복 오류/시간 소진은 중단 |

Kafka의 committed offset은 재시작 시 읽을 다음 위치다. 파티션의 offset 0·1을 완료했다면 committed=2다.
이 프로젝트는 파티션 내부 동기 처리를 유지한다. 다른 파티션이 먼저 끝나도 미완료 파티션을 건너뛰지 않는다.
한 파티션에서 여러 future를 동시에 실행하고 순서 없이 ACK하는 구조는 아직 도입하지 않았다.

완료 후 재전달에서는 공급자를 다시 호출하지 않지만, 공급자 수락 후 DB 기록 전에 실패하면 재호출이 가능하다.
따라서 정상 실험의 관측 중복0을 외부 exactly-once로 일반화할 수 없다. DB lease 만료도 이미 시작한 외부 호출을 취소하지 않는다.

## 3. 병렬 처리·배포: 병목을 확인하고 작업 소유권을 유지하며 늘린다

### 문제 상황과 선택 기준

요청을 빨리 접수하는 것과 대상을 빨리 발송하는 것은 다른 목표다.
API를 늘려도 Worker나 공유 DB가 병목이면 발송 처리량은 그대로일 수 있다.
Worker를 늘릴 때에는 파티션·처리 자리·DB/HTTP 풀·전체 quota와 완료 offset을 함께 확인해야 한다.

| 방법 | 기대 효과 | 비용과 현재 판단 |
| --- | --- | --- |
| Consumer와 활성 작업 상한 증가 | 여러 파티션의 작업 동시 처리 | DB/CPU 사용량과 실시간 접수 지연도 관찰. 실험1/1·2/2·3/3 비교, 기본1/1 유지 |
| 파티션3→6 | 분배 단위를 늘림 | key mapping·기존 기록의 순서·신규 offset·복구 보존 용량 영향이 있어 기본3 유지 |
| 압축·동시 제출 창 | 전송 byte/ACK 대기 비용 변경 | broker 단독 결과와 앱 결과가 달라 실제 HTTP 경로를 별도 비교, none/제출1 기본 유지 |
| 가상 스레드 | I/O 대기 자원 사용 방식 변경 | 외부 I/O 주병목 근거가 부족해 비교 미실행 |
| API/Worker의 프로세스 분리 | 접수 분산과 소비 재배정 경계 확인 | 같은 DB·공급자 예산·호스트 장애는 공유하므로 별도 검증 필요 |

LB는 HTTP 접수를 API에 나누고, Kafka consumer group은 파티션을 Worker에 나눈다.
같은 group의 파티션 소유권 재배정이 Worker 분산 처리의 축이다.
현재 요청 토픽이3파티션이면 그 토픽을 동시에 소비하는 소유자는 최대3개다.
요청/Retry 총6파티션을 가진다고 정상 요청 토픽의 병렬도가6이 되는 것은 아니다.

### 공유 DB 쿼리도 분리의 효과를 제한했다

역할별 토픽과 풀을 나눈 뒤에도, 실시간 선점 SELECT가 캠페인 작업까지 잠그는 문제를 재현했다.
인덱스가 있다는 사실과 실제 선택된 접근 경로·잠금 범위가 같지 않았다.

| 진단 단계 | 실제 관측 | 판단과 변경 |
| --- | --- | --- |
| 기본 자동 통계·적재 직후 | status 인덱스 선택, PRIMARY 잠금 레코드100001개·캠페인 기존 행 갱신 대기 | 역할 접두사 인덱스 경로를 명시 |
| 인덱스만 명시(중간 실행은FAIL) | PRIMARY 잠금 레코드1개로 감소해도 캠페인 선점의 gap/insert-intention 대기 남음 | 선점의 짧은 트랜잭션에 READ COMMITTED 적용 |
| 최종 대조군 포함4조건 | PRIMARY/보조 인덱스 각각1개, holder에 의한 세 종류 대기 미관측 | 행 잠금·lease fencing 유지, 해당 선점 경계만 변경 |

조건은 MySQL8.4.8/2CPU·2GiB/buffer512MiB, 캠페인100000+실시간100 PENDING이었다.
트랜잭션을 의도적으로 약1초 유지하며 data_locks/data_lock_waits를 관찰했다.
잠금 레코드 수는 고유 업무 행 수나 실행 시간의 배수가 아니다. 이 결과를100만 배 속도 개선으로 해석하지 않는다.
전체 DB 격리 수준을 바꾸지 않았으며, FK/중복 검사 등의 모든 gap 대기가 사라졌다는 뜻도 아니다.
초기 EXPLAIN-only 계측의 잠금 집계가 비어 있었을 때도 경합이 없다고 결론 내리지 않았다.
실제 SELECT 실행과 RECORD 잠금 존재 확인으로 관측 방법을 보완한 뒤 위 전후를 대조했다.
인덱스만 명시한 중간 진단은 음성 대조군의 빈 결과를 잘못 실패 처리해 전체 FAIL이었다.
그 실행에서 앞서 수집한 gap 대기 관측을 보존했고, 보완한 최종4조건 PASS와 구분한다.
현재 SQL은 [OutboxStore](../src/main/java/dev/jinhyeon/notificationlab/outbox/OutboxStore.java),
당시 전후·계측 실패·대조군은 [잠금 진단](S7_OUTBOX_CLAIM_LOCKS.md)에 보존했다.
InnoDB의 잠금 접근 경로는 [MySQL 8.4 공식 문서](https://dev.mysql.com/doc/refman/8.4/en/innodb-locks-set.html)를 참고한다.
이 SQL 문제를 최초 API5초 timeout의 확정 원인으로 연결하지 않는다.

### 기본값을 유지한 이유

현재 기본은 Consumer/활성/대기 **1/1/2**, 요청/Retry/DLQ 각3파티션, 동기 RECORD,
Relay 제출/완료 저장1/1, producer none/linger0, in-process Mock100ms다.
Redis quota·역할 분리·Circuit Breaker는 선택 기능이며 기본 OFF다.

실험에서 특정 설정이 더 빠르게 관측됐어도 DB/CPU·실시간 지연 비용과 표본 변동을 함께 봤다.
배포 구성에서 안전하게 동작하는지와 운영 최적 용량인지는 별개라 기본값을 자동으로 올리지 않았다.
COUNT_TIME의 별도10만 건 비교도 있었지만 실시간 지연 비용과 오류 경계를 고려해 RECORD를 유지했다.
[커밋 방식 비교](S7_OFFSET_100K.md)와 [현재 설정](../src/main/resources/application.yml)을 함께 확인한다.
